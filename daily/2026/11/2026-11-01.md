## 核心判断

**Agent 工程化正在形成两条不同但互补的路径：① 主动执行之前的授权/人工注意力治理与沙箱凭证隔离；② 将“下一步行动”收敛为有限、可重放的决策，而非每一步都依赖自由文本生成。** 同时，Android 后台虚拟屏和桌面多 Agent 团队呈现新热度。相较前期已有的 Kiro Crew/Orca/OpenBot，本期新增证据更强调**执行授权的宿主强制边界、凭证代理以及决策轨迹**。

## 1. DeepSeek dsh-superagent：带宿主授权门禁的主动 Coding Agent 原型

- **官方仓库：** https://github.com/deepseek-ai/dsh-superagent-prototype ，MIT；**2,220 Stars / 190 Forks**（REST 观测），创建于 **2026-10-31**；首次收录。
- **定位边界：** README 明确声明 **“research prototype for reference only, not an official DeepSeek product”**。它是 DeepSeek Harness 的研究性 Bundle，监听 GitHub Issue/PR/CI，及可选飞书消息，为单个 GitHub 仓库创建 Ticket、独立 Session 和工作目录；不是正式产品发布，也不是通用多租户托管服务。
- **关键技术：** `docs/002-authorization.md` 将明确请求、推断候选与仅供上下文的订阅消息分开；宿主执行允许名单、规则、Mandate 与 Policy 版本；推断任务默认 `observe`（只记录“本可接受”），需明确切换 `auto`。`docs/003-execution.md` 定义 Worker 并发槽、后台作业、人工接管、恢复和任务回放。
- **安全边界：** 官方文档同时承认 Worker **以操作者 OS 用户身份无需审批执行命令**，命令黑名单和目录只是默认约束，**不是安全隔离**。因此“宿主授权门禁”不等于执行沙箱。重点复验提示注入、被授权请求的范围扩张、任务重试幂等和 OS 权限。
- **一手资料：** https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/002-authorization.md ；https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/003-execution.md 。

## 2. RudderStack DevBox：每任务独立沙箱 + 出站代理注入真实凭证

- **官方仓库：** https://github.com/rudderlabs/devbox ，MIT；**259 Stars / 15 Forks**（官方搜索与仓库页面的非原子观测），创建于 **2026-10-27**；首次收录。低 Star 不影响其明确的架构信号。
- **技术差异：** 从 Linear/GitHub 任务到 Plan → Plan Review → Implement → Self Review → Draft PR；每个任务由 OpenSandbox 启动独立容器。Sandbox 内只持有占位 Token，`iron-proxy` 在出站流量中注入真实 GitHub/模型凭证并限制目标仓库；Control Plane 自身不执行模型推理。任务工作区 Volume 可在 Sandbox 销毁后保留，用于恢复和审阅反馈。
- **注意：** 官方称内部 PR 采用率和合并率较高，但未经独立验证；代理网络隔离、容器逃逸、DNS/直连绕过及凭证可见性仍需渗透测试。它与此前 OpenBot 的“独立浏览器/文件”相比，把**凭证不进入 Agent 执行环境**落实为可审计的网络架构。
- **一手资料：** https://github.com/rudderlabs/devbox/blob/main/docs/architecture.md 。

## 3. switch：有限决策模型获得可重放的 Agent Harness

- **官方仓库：** https://github.com/osolmaz/switch ，MIT；**383 Stars / 27 Forks**，创建于 **2026-10-25**；首次收录。
- **技术路线：** 与普通 Coding Agent 自由生成文本和工具调用不同，switch 让应用代码定义 `Domain / State / Question / Transition`，模型只回答 `bool / choice / score` 等类型化问题及概率；工具调用由宿主根据有限选项执行。每一步状态、问题、答案形成 Trace，可不调用模型进行 Replay。
- **科研价值：** 可将 PDF/Word/Markdown 等复杂成果评审转化为按需读取证据的分步判定，而不是一次性塞入全文；适合研究**低成本决策层、可解释状态转移和确定性复现**。
- **证据边界：** README 坦言当前 Jev 在棋类/评审任务尚不足以替代强聊天模型；“成本降到百分之一”是方向性设想，**不是已验证性能**。与已跟踪的 `strands-decider` 相比，新意在领域状态机 + 工具宿主 + Trace/Replay 的通用 Harness。
- **一手资料：** https://github.com/osolmaz/switch 。

## 4. Mika：Android 后台虚拟屏 Computer Use

- **官方仓库：** https://github.com/wangzan101/Mika ，Apache-2.0；**2,703 Stars / 436 Forks**（官方搜索与仓库页面观测），创建于 **2026-10-29**；首次收录。
- **技术差异：** Android 11+ 上通过无线调试配对，在独立后台虚拟屏操作 App，用户可同时继续使用前台手机；可观察执行过程，网页交互支持用户接管。每个会话可使用本机 ARM64 Linux 沙箱处理文件/运行脚本，并通过 CLI/MCP 接收电脑 Agent 的任务。
- **边界：** “本地优先”不等于所有模型推理离线：使用第三方模型 API/账号时，相关请求可能离开设备。无线调试授权、虚拟屏可访问数据、支付前确认和跨 App 会话隔离需要实测。与 Browser Agent 及此前 OpenBot 的桌面/云浏览器不同，这里是**手机端原生 App 的后台操作面**。
- **一手资料：** https://github.com/wangzan101/Mika/blob/main/README.md ；https://github.com/wangzan101/Mika/blob/main/docs/setup-guide.md 。
